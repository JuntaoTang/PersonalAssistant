# 课程背景与项目原则

本文件摘录课程文件夹中的 `notes.md` 和 `proj/requirement/lab1.md`，供本仓库独立阅读。摘要更新于 2026-10-13；完整讲义保留在课程文件夹的 `lec/` 中。后续课程要求变化时同步修订本摘要。

## Lab 1 的目标

实验为建议性质、不记分，目标是构建会持续工作、能够吸收纠正的个人助手，包含五项基础能力：

1. **个人资料库**：索引和检索资料，随原文变化更新，回答能定位来源；推荐可读、可编辑的 Markdown。
2. **smail 邮箱**：持续获取新邮件、关联历史往来，结合资料准备可编辑的回复草稿，只发送用户确认的最终稿；重复检查不重复处理或发送。
3. **ehall 事务**：查询信息，完成至少一种事务的材料准备和表单填写；提交前展示关键字段与后果并取得确认，不能自行退课或撤销申请。
4. **手机联动**：手机能发起任务、查看进度、编辑草稿和确认操作，任务不依赖桌面端始终打开的聊天窗口。
5. **能力组合**：共享必要上下文，完成至少一条用户愿意反复使用的完整流程。

成功流程和用户纠正应保存为可读、可修改的脚本、规则或记忆，并用 Git 管理。在新会话和另一份材料中验证纠正继续生效。

## 讲义中用于本项目的建议

- 先将意图变成可验收行为，区分已确认、禁止和未决事项，并写清失败情形。
- 用小版本获得实际反馈，尽早验证最不确定的环节；人继续负责目标、接口和高返工代价的决定。
- 按职责、接口和数据归属组织模块，用“改一处需求会牵动多少处实现”检查架构。
- 工具通过明确的文本或结构化接口组合，中间结果可以查看；先厘清边界，再按需要增加基础设施。
- 明确事实来源，索引和缓存由事实推导并可以失效、重建；结论与决定保留依据。
- 模型负责理解与受约束的建议，程序校验和执行；查询、草稿、确认、执行分开，重试不重复产生外部副作用。
- 用与风险相称的测试和实际操作留存证据；局部演示或测试通过不等于整个系统已完成。
- 保持上下文简洁，稳定规则放 `AGENTS.md`；需求、实现、规则和验证一起做可恢复的小步提交，凭据与私人运行数据不入库。

本项目的具体选择与进度见 [requirements.md](../requirements.md)，实现边界见 [architecture.md](../architecture.md)，证据与未验证范围见 [validation.md](../validation.md)。
